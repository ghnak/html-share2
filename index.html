Interface & Address Management
ip addr Show IP addresses and interface state — always run this first
net★ start here
▾
The first command to run on any device. Shows every interface, its IP address, subnet mask, MAC address, and whether it's UP or DOWN. Modern replacement for the old ifconfig.
bash
$ ip addr show            # full output, all interfaces
$ ip a                     # shorthand
$ ip -br a               # brief: one line per interface
$ ip -br -c a            # brief + color (easiest to read)
$ ip addr show eth0        # specific interface only
$ ip -4 addr show          # IPv4 only
# Temporary static IP (lost on reboot):
# ip addr add 192.168.1.99/24 dev eth0
Reading the output
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500UP = enabled, LOWER_UP = cable connected ✓
link/ether 00:11:22:33:44:55MAC address (hardware ID)
inet 192.168.1.50/24 brd 192.168.1.255/24 = subnet 255.255.255.0 ✓
<BROADCAST,MULTICAST,UP> — no LOWER_UP⚠ interface on but no cable / no link
<BROADCAST,MULTICAST> — no UP✗ interface disabled → sudo ip link set eth0 up
(no inet line at all)✗ no IP assigned — DHCP failed or not configured
UP + LOWER_UP + inet = normal
UP only = no cable
No inet = no IP assigned
🔧 FSE Scenario — "I can't reach the sensor at 192.168.1.10"

Step 1: ip -br a on your machine — does eth0 show a 192.168.1.x/24 IP? If it shows 169.254.x.x, DHCP failed — set a static IP or fix the DHCP server.

Step 2 — No IP: sudo dhclient eth0 to request DHCP, or: sudo ip addr add 192.168.1.99/24 dev eth0 && sudo ip link set eth0 up

Step 3: SSH into the sensor, run ip a there. If it got a new DHCP address, use nmap -sn 192.168.1.0/24 to find it.

ip link Bring interfaces up/down — enable or reset a network interface
net
▾
Controls whether a network interface is enabled. Use when ip a shows an interface is DOWN, or to reset a flapping interface by cycling it down and back up.
$  ip link show                  # list all interfaces + state
#  ip link set eth0 up           # enable interface (needs sudo)
#  ip link set eth0 down         # disable interface
# Reset a flapping / stuck interface:
#  ip link set eth0 down && sleep 2 && ip link set eth0 up
$  ip -s link show eth0           # TX/RX stats + error counters
🔧 Scenario — interface DOWN after reboot

ip -br a shows eth0 DOWN with no IP. Quick fix: sudo ip link set eth0 up && sudo dhclient eth0. Permanent fix: edit /etc/netplan/*.yaml, ensure dhcp4: true for the interface, then sudo netplan apply.

ip route Routing table — where does each packet get sent?
net★ essential
▾
The routing table decides the next hop for every packet. Without a default route, the device can only reach its local subnet — the C2 server, VPN, and internet are all unreachable. Very common on freshly imaged sensors.
$ ip route show              # full routing table
$ ip r                        # shorthand
$ ip route get 10.0.0.5       # which route handles C2?
$ ip route get 8.8.8.8        # which route handles internet?
# Fix missing default gateway (sudo):
# ip route add default via 192.168.1.1 dev eth0
# ip route del default
# ip route add 10.0.0.0/8 via 192.168.1.1  # static route to VPN subnet
Normal vs. broken routing table
default via 192.168.1.1 dev eth0 proto dhcp✓ default gateway present — internet reachable
192.168.1.0/24 dev eth0 proto kernel scope link✓ local subnet route
(only: 192.168.1.0/24 ... no default)✗ no default! C2 and internet unreachable
🔧 Scenario — sensor pings gateway but not C2

ping 192.168.1.1 works. ping 10.0.0.5 fails with "Network unreachable."
Run ip route show — no default line. Fix: sudo ip route add default via 192.168.1.1 then retest. For persistence, update Netplan config.

Connectivity Testing — ping & traceroute
ping Test reachability and latency — always your first step
net★ start here
▾
Sends ICMP echo requests to check if a host responds. Always work outward: loopback → own IP → gateway → internet IP → C2 server. The first hop that fails shows you exactly which layer the problem is in.
$ ping -c 4 192.168.1.1         # test gateway
$ ping -c 4 8.8.8.8             # test internet reachability
$ ping -c 10 -i 0.2 10.0.0.5   # 10 packets fast to C2
$ ping -c 100 -q 192.168.1.10   # 100 packets quiet — reliable loss %
$ ping -s 1472 192.168.1.10     # large packet — MTU path test
$ ping -W 1 192.168.1.10        # 1s timeout — quick dead-check
5-hop isolation checklist — run in order
$ ping -c2 127.0.0.1       # 1. loopback   — fail = OS/stack broken
$ ping -c2 192.168.1.50     # 2. own IP     — fail = interface down
$ ping -c2 192.168.1.1      # 3. gateway    — fail = LAN/cable issue
$ ping -c2 8.8.8.8          # 4. internet   — fail = WAN/route missing
$ ping -c2 google.com        # 5. hostname   — fail = DNS broken
Interpreting results
64 bytes from 192.168.1.1: time=1.2 ms✓ fast local LAN response
64 bytes from 8.8.8.8: time=45 ms~ normal internet RTT
64 bytes from 10.0.0.5: time=920 ms✗ severe congestion or link problem
Request timeout for icmp_seq 3packet dropped or ICMP blocked by firewall
10 tx, 10 rx, 0% packet loss✓ perfect
10 tx, 7 rx, 30% packet loss✗ bad cable, WiFi interference, overloaded link
⚠ Gotcha — ping passes but the application still fails

ICMP ≠ TCP. Ping only tests ICMP echo — it does NOT prove that port 443, 8080, or 1883 is open or that the service is running. A firewall can allow ICMP but block TCP ports.

After ping succeeds: use ss -tulpn to verify the port is listening, or curl -v http://10.0.0.5:8080 to test the actual endpoint.

🔧 Scenario — ~30% packet loss to sensor, connection flaky

Run ping -c 200 -i 0.1 -q 192.168.1.10 for a statistically reliable sample. Also check ip -s link show eth0 on both sides — if TX/RX error counters are rising, suspect a bad cable, PoE power issue, or faulty switch port.

traceroute / mtr Trace every router hop — pinpoint exactly where packets die
net★ essential
▾
Where ping tells you if connectivity is broken, traceroute tells you where. Each line = one router hop. mtr (My TraceRoute) runs continuously and shows per-hop packet loss live — the upgraded version.
$ traceroute 10.0.0.5                  # trace to C2
$ traceroute -n 10.0.0.5               # skip DNS (faster)
$ traceroute -T -n -p 443 10.0.0.5    # TCP mode on port 443 (bypasses ICMP blocks)
$ mtr 10.0.0.5                          # live view (q to quit)
$ mtr --report --report-cycles 20 -n 10.0.0.5  # 20-cycle report
Reading the output
1 192.168.1.1 1.2 ms 1.1 msyour gateway — fast, normal ✓
2 10.0.1.1 8.4 ms 7.9 msISP first hop — acceptable
3 * * *blocks ICMP probes — not necessarily broken, keep reading
4 10.0.0.5 15 ms 14 msdestination reached ✓ — all good
5 172.16.0.1 280 ms 290 ms✗ sudden spike — congestion at this hop
6 * * *packets stop here → firewall or routing black hole
7 * * *never reaches destination
KEY INSIGHT Mid-path * * * is usually fine — routers often drop ICMP probes. Only worry if the final destination shows loss or is never reached.
🔧 Scenario — C2 connection drops every ~5 minutes

Likely a NAT/firewall timeout killing idle TCP connections. Confirm with mtr --report -n 10.0.0.5 — if all hops show 0% loss, the path is fine and the problem is NAT session expiry. Fix: enable TCP keepalives in the sensor app config, or add ServerAliveInterval 30 to SSH config.

Ports & Socket Monitoring
ss Socket statistics — see every open port and active connection
net★ essential
▾
Modern replacement for netstat. Shows all TCP/UDP sockets — what's listening, what's actively connected, which process owns each socket. Use to confirm a service is listening on the expected port, or that a C2 connection is actually established.
$ ss -tulpn               # ALL listening ports + process — run this first
$ ss -tnp                # established TCP connections + process
$ ss -s                  # summary statistics
$ ss -tulpn | grep :8080 # is something on port 8080?
$ ss dst 10.0.0.5        # connections TO C2 server
$ ss state established   # only live/active connections
Understanding the output
tcp LISTEN 0.0.0.0:22 sshdSSH listening on all IPs ✓
tcp LISTEN 127.0.0.1:8080 rfpatrol⚠ localhost only — not reachable from network
tcp LISTEN 0.0.0.0:8080 rfpatrol✓ accessible from any IP on network
tcp ESTAB 192.168.1.10:54321 → 10.0.0.5:443✓ live C2 connection exists
tcp CLOSE-WAIT 192.168.1.10:54322✗ hung socket — app not closing connections
FlagMeaningUse when
-tTCP onlyMost services use TCP
-uUDP onlyDNS, DHCP, SNMP, syslog
-lListening sockets onlyWhat ports are open?
-pProcess name + PIDWhich app owns this port?
-nNumeric (no DNS)Faster output
-sSummary statisticsQuick health overview
🔧 Scenario — "API service is running but nobody can connect to port 8080"

1 — Is it listening? ss -tulpn | grep :8080
Nothing → service failed to start or is on a different port. Check journalctl -u rfpatrol -n 50.

2 — Where is it listening? If you see 127.0.0.1:8080, the app is bound to localhost only — not reachable from the network. Fix the app's bind config to 0.0.0.0 and restart.

3 — Firewall? sudo ufw status. If ufw is active: sudo ufw allow 8080/tcp

netstat Classic network stats — common on older devices and legacy scripts
net
▾
May not be installed on Ubuntu 22+. Install: sudo apt install net-tools. Prefer ss on modern systems, but you'll encounter netstat in older documentation and scripts.
$ netstat -tulpn    # listening ports + process (same as ss -tulpn)
$ netstat -rn       # routing table, numeric
$ netstat -i        # interface stats: TX/RX bytes, errors
$ netstat -an | grep ESTABLISHED
Old (netstat)Modern equivalent
netstat -tulpnss -tulpn
netstat -rnip route show
netstat -iip -s link show
Packet Capture — tcpdump
tcpdump Capture raw network packets — the ground-truth debugger
netadvanced
▾
When everything else claims the network is fine but the application still fails, tcpdump shows you the raw wire-level truth. You can see exactly which packets are sent, received, or dropped. Run on both the sensor and C2 simultaneously to compare what each side sees.
# Basic captures:
# tcpdump -i eth0 -n                    # all traffic, no DNS lookup
# tcpdump -i any -n                     # all interfaces

# Filter by host or port:
# tcpdump -i eth0 host 10.0.0.5        # all traffic to/from C2
# tcpdump -i eth0 port 443             # HTTPS only
# tcpdump -i eth0 host 10.0.0.5 and port 443
# tcpdump -i eth0 src 192.168.1.10    # only FROM sensor
# tcpdump -i eth0 not port 22          # exclude SSH noise

# Save to file — open in Wireshark on your laptop:
# tcpdump -i eth0 -w /tmp/cap.pcap -n -c 5000
# tcpdump -r /tmp/cap.pcap              # read saved capture

# Read HTTP plaintext content:
# tcpdump -i eth0 -A -n port 80        # ASCII output
TCP flags — diagnose connection states
192.168.1.10 → 10.0.0.5: Flags [S]SYN: sensor attempting to connect
10.0.0.5 → 192.168.1.10: Flags [S.]SYN-ACK: C2 responded, handshake proceeding ✓
192.168.1.10 → 10.0.0.5: Flags [.]ACK: connection established ✓
10.0.0.5 → 192.168.1.10: Flags [R.]RST: connection refused — port closed or app rejected
192.168.1.10 → 10.0.0.5: Flags [S] (no reply...)SYN only — C2 unreachable or firewalled
🔧 Scenario — sensor says it's connected to C2 but data never arrives

On sensor: sudo tcpdump -i eth0 -n host 10.0.0.5 — do you see SYN → SYN-ACK → ACK handshake? Do you see PSH (data) packets going out? If yes, sensor is sending.

On C2 (if accessible): sudo tcpdump -i any -n src 192.168.1.10
Packets arriving? → Problem is in C2 application, not the network. Check C2 service logs.
Packets NOT arriving? → Something in the network is dropping them. Use traceroute to isolate where.

FSE TIP Save to /tmp/cap.pcap, copy home: scp user@sensor:/tmp/cap.pcap ~/Desktop/, open in Wireshark for full protocol analysis and stream reconstruction.
DNS Troubleshooting
dig / nslookup DNS lookup — diagnose "hostname not resolving" failures
netdns
▾
DNS is a silent killer — the device has full IP connectivity (ping 8.8.8.8 works) but anything using a hostname fails. DNS issues are also common after DHCP renewals if the DNS server assignment changes.
$ dig +short google.com           # quick IP answer
$ dig google.com                   # full detail output
$ dig @8.8.8.8 google.com          # bypass local DNS, use Google directly
$ dig @192.168.1.1 google.com      # test local/gateway DNS
$ dig -x 8.8.8.8                   # reverse: IP → hostname
$ nslookup google.com              # simpler alternative
$ nslookup google.com 8.8.8.8      # specify DNS server
$ cat /etc/resolv.conf             # what DNS server is configured?
$ resolvectl status                # systemd-resolved (Ubuntu 20+)
Reading dig output
google.com. 299 IN A 142.250.70.14✓ resolved — DNS working
;; SERVER: 127.0.0.53#53127.0.0.53 = systemd-resolved local stub
;; Query time: 12 msecfast response ✓
;; connection timed out; no servers could be reachedDNS server unreachable
NXDOMAINhostname doesn't exist in DNS — typo or missing record
SERVFAILDNS server error — try a different server
🔧 Scenario — "ping 8.8.8.8 works but ping google.com fails"

Classic DNS failure. IP connectivity is fine but hostname resolution isn't.

1: cat /etc/resolv.conf — is there a nameserver line?
2: dig +short google.com @8.8.8.8 — bypass local DNS. If this works, your local DNS server is the problem.
3: resolvectl status — is systemd-resolved running?
Quick fix: echo "nameserver 8.8.8.8" | sudo tee /etc/resolv.conf (temporary — overwritten by DHCP on reconnect)

HTTP Testing with curl
curl Test HTTP/HTTPS endpoints — APIs, web UIs, health checks
net★ essential
▾
curl speaks HTTP — the actual proof that an API or web UI is working end-to-end, beyond what ping or ss can tell you. The -v flag exposes every header and error message, making it the best single tool for diagnosing application-layer failures.
$ curl http://192.168.1.10:8080/api/status
$ curl -v http://host/api           # verbose: show all headers
$ curl -I http://host               # HEAD only (headers, no body)
# Just the HTTP status code — great for scripts:
$ curl -o /dev/null -s -w "%{http_code}\n" http://host:8080/health
200  ← healthy   000 ← refused   502 ← bad gateway   401 ← auth fail
# HTTPS with self-signed cert (common on sensors):
$ curl -k https://192.168.1.10
# Fail fast (useful in troubleshooting scripts):
$ curl --connect-timeout 5 -m 10 http://host/api
# POST to REST API:
$ curl -X POST \
       -H "Content-Type: application/json" \
       -H "Authorization: Bearer TOKEN" \
       -d '{"sensor_id":"mk2-001"}' \
       http://10.0.0.5/api/register
Reading verbose (-v) output
* Trying 10.0.0.5:443...attempting TCP connection
* Connected to 10.0.0.5 port 443TCP layer OK ✓
* TLS 1.3 — TLS handshake succeededTLS/SSL OK ✓
> GET /api/status HTTP/1.1request sent →
< HTTP/1.1 200 OKserver responded correctly ✓
* connect to 10.0.0.5 failed: Connection refusedport closed — service not running
* SSL certificate verify failedcert expired or self-signed — use -k to bypass
< HTTP/1.1 401 Unauthorizedauth token wrong or expired
🔧 Scenario — sensor fails to POST detections to C2 API

Sensor logs show ERROR: POST /api/events → 401 Unauthorized.

Reproduce from sensor: curl -v -k -X POST -H "Authorization: Bearer TOKEN" https://10.0.0.5/api/events -d '{}'
If 401 → auth token wrong or expired. Check sensor config file for the token and compare with what C2 expects. Token rotation without updating sensor config is the usual cause after upgrades.
If 000 (Connection refused) → API service is down on C2. SSH to C2 and check systemctl status api-server && journalctl -u api-server -n 50.

SSH Remote Troubleshooting
ssh Remote access, command execution, and port forwarding
sys★ essential
▾
SSH is the primary tool for all remote sensor work — beyond basic login it lets you run commands without a shell, forward ports to reach web UIs behind NAT, and jump through bastion hosts.
# Connect:
$ ssh ubuntu@192.168.1.10
$ ssh -p 2222 ubuntu@192.168.1.10
$ ssh -i ~/.ssh/sensor.pem ubuntu@192.168.1.10

# Run a single command without interactive shell:
$ ssh ubuntu@192.168.1.10 "ip a; ip r; ss -tulpn"
$ ssh ubuntu@192.168.1.10 "systemctl status rfpatrol"
$ ssh ubuntu@192.168.1.10 "journalctl -u rfpatrol -n 100 --no-pager"

# Debug connection failures:
$ ssh -v ubuntu@192.168.1.10      # verbose auth debug
$ ssh -vvv ubuntu@192.168.1.10    # very verbose

# Port forwarding — access sensor web UI from your laptop:
$ ssh -L 8080:localhost:80 ubuntu@192.168.1.10
  → open http://localhost:8080 to reach sensor's port 80

# Background tunnel (no shell, stays running):
$ ssh -N -f -L 8080:localhost:80 ubuntu@192.168.1.10

# Jump through bastion host to reach sensor:
$ ssh -J user@bastion.example.com ubuntu@192.168.1.10

# Prevent idle timeout (add to ~/.ssh/config):
$ ssh -o ServerAliveInterval=30 -o ServerAliveCountMax=6 ubuntu@192.168.1.10
SSH debug output (-v) — what each line means
debug1: Connection established.TCP layer works ✓
debug1: Offering public key: ~/.ssh/sensor.pemtrying key auth
debug1: Authentication succeeded (publickey).key accepted ✓
ssh: connect to host ... port 22: Connection refusedsshd not running — check port or start sshd
ssh: No route to hostrouting problem — check ip route on your machine
debug1: Permission denied (publickey).key not in ~/.ssh/authorized_keys on server
🔧 Scenario — SSH session freezes then drops after a few minutes

A NAT/firewall between you and the sensor is killing idle TCP connections. Fix — add to ~/.ssh/config:
Host 192.168.1.*
    ServerAliveInterval 30
    ServerAliveCountMax 6
Also use tmux or screen on the remote end so sessions survive unexpected disconnects.

💡 Pro tip — ~/.ssh/config saves hours

Name all your sensors so you never type long commands again:

Host sensor1
  HostName 192.168.1.10
  User ubuntu
  IdentityFile ~/.ssh/sensor.pem
  ServerAliveInterval 30

Then: ssh sensor1, scp sensor1:/var/log/app.log ./ — all work automatically.

Log Analysis — journalctl
journalctl Query systemd journal — diagnose service failures and network events
log★ essential
▾
On Ubuntu, all service and system events flow through the systemd journal. When a sensor service fails, the C2 connection drops, or the network flakes out — the answer is in here. The key skill is filtering efficiently to find relevant messages fast.
# Service logs:
$ journalctl -u rfpatrol               # all logs for a service
$ journalctl -u rfpatrol -f            # follow live (Ctrl+C to stop)
$ journalctl -u rfpatrol -n 100        # last 100 lines
$ journalctl -u rfpatrol --no-pager    # pipe to grep without paging

# Filter by time — key for "it broke overnight":
$ journalctl --since "1 hour ago"
$ journalctl --since "2024-01-20 22:00" --until "2024-01-21 06:00"
$ journalctl -b                         # since last boot
$ journalctl -b -1                      # PREVIOUS boot — find crash cause

# Filter by severity (fastest triage):
$ journalctl -p err                    # errors only
$ journalctl -p err -u rfpatrol        # errors for specific service

# Network-specific:
$ journalctl -u NetworkManager         # NM connection events
$ journalctl -u systemd-networkd       # networkd interface events
$ journalctl -k                         # kernel messages (like dmesg)
$ journalctl -k | grep -i "eth\|link\|error"
Key log messages to recognise
rfpatrol[1234]: Connected to C2 at 10.0.0.5:443✓ normal
rfpatrol[1234]: Connection to C2 failed: timeout✗ network unreachable or C2 down
rfpatrol[1234]: TLS handshake failed: certificate expired✗ cert issue — check expiry dates
rfpatrol[1234]: HTTP 401 Unauthorized✗ auth token wrong or expired
NetworkManager: eth0: link is not ready⚠ cable disconnected or switch port down
systemd-networkd: eth0: DHCPv4 request timed out✗ no DHCP server response
kernel: eth0: renamed from eth1⚠ interface renamed after reboot — configs may break
🔧 Scenario — "Service was fine yesterday but failed overnight"

Step 1: Find when it stopped: journalctl -u rfpatrol -b -1 --no-pager | tail -100 — spot the last success and the first error.

Step 2: Cross-reference network events at the same time: journalctl -u NetworkManager --since "yesterday 20:00" --until "today 06:00"

Common overnight culprits: DHCP lease expired → sensor got new IP; VPN cert expired at midnight; interface renamed after kernel update (eth0 → enp3s0); disk filled up from log rotation.

Additional Tools
nmap Network scanner — find all hosts and open ports on a subnet
netscan
▾
Use to discover all devices on a subnet, find a sensor with an unknown DHCP address, or confirm which ports are open on a host.
$ nmap -sn 192.168.1.0/24          # find all live hosts
$ nmap 192.168.1.10                  # scan common ports
$ nmap -p 22,80,443,8080 192.168.1.10
$ nmap -sV 192.168.1.10              # detect service versions
PORT     STATE  SERVICE  VERSION
22/tcp   open   ssh      OpenSSH 8.9
8080/tcp open   http     RfPatrol API v2.1
CAUTION Only scan networks you own or have explicit permission to scan. Port scanning can trigger IDS/IPS alerts at customer sites.
iperf3 Measure actual network bandwidth between two hosts
netperf
▾
Proves whether a slow C2 connection is a network bandwidth problem or an application problem. Run server on C2, client on sensor.
# On C2 / remote host:
$ iperf3 -s
# On sensor / client:
$ iperf3 -c 10.0.0.5
$ iperf3 -c 10.0.0.5 -t 30     # run for 30s

SSH Tunneling Forward ports through SSH — access remote web UIs and services
sysnet
▾
Access remote web interfaces as if they were running locally.
# LOCAL FORWARD: access remote:80 via localhost:8080
$ ssh -L 8080:sensor-ip:80 user@jump-host
  → then open browser: http://localhost:8080

# REMOTE FORWARD: expose local port to remote server
$ ssh -R 9000:localhost:22 user@remote-server

# SOCKS PROXY: route all traffic through SSH
$ ssh -D 1080 user@jump-host
  → configure browser proxy: SOCKS5 127.0.0.1:1080

# Keep tunnel running (no shell):
$ ssh -N -f -L 8080:sensor:80 user@jump-host
scp / rsync Securely copy files to/from remote hosts
sys
▾ 
# scp: simple one-time copies
$ scp user@192.168.1.10:/var/log/app.log ./  # pull log
$ scp config.yml user@192.168.1.10:/etc/app/ # push config
$ scp -r user@host:/data/logs/ ./logs/       # recursive

# rsync: smarter (only copies changed files)
$ rsync -avz user@host:/var/log/ ./remote-logs/
$ rsync -avz --progress ./local/ user@host:/remote/
TIP Prefer rsync for large log transfers — it resumes interrupted transfers.
